## Build

```bash
firmware/build.sh            # prints build_seconds, binary sizes, the manifest and work_dir
```

Each checkout (main or a task worktree) builds in its own scratch copy, `~/Projects/weixue-vendor/fw-work/<checkout dir name>` (for example `fw-work/weixue-wt-feat-firmware-base`), so parallel tasks never share build state. The first build of a scratch copy is a full build and downloads managed components from components.espressif.com. The mirror keeps the generated `main/assets/lang_config.h`; ninja regenerates it when the language or its `language.json` changes. `build.sh` stops with `dependencies.lock differs` when the component manager resolved different managed components than `firmware/dependencies.lock`, and writes no manifest; after an intentional component update, copy `<work_dir>/dependencies.lock` to `firmware/dependencies.lock`, commit it and rebuild. Changing the backend address means editing `CONFIG_OTA_URL` in `firmware/board/config.weixue.json` and rebuilding.

`WEIXUE_FACE_DIAG=1 firmware/build.sh` builds the face diagnostics in (see Face); without it `build.sh` builds them out. The flag is written to the scratch copy's `face_diag.h`, so switching it recompiles only the face sources.

`WEIXUE_FACE_DIAG=1 WEIXUE_AUDIO_DEBUG_UDP=<ipv4>:<port> firmware/build.sh` also enables the upstream audio debugger (`CONFIG_USE_AUDIO_DEBUGGER`): every microphone read (16 kHz, interleaved microphone and playback reference, int16) is sent as one UDP datagram to that address, in idle as well. `build.sh` refuses the knob without `WEIXUE_FACE_DIAG=1` and fails a build without it whose sdkconfig has the debugger on.

## Source patches

`build.sh` mirrors the vendored clone into the scratch copy with `rsync --delete`, so edits made in the scratch copy are lost on the next build. New files live in `firmware/overrides/` under their path in the clone; `build.sh` stops if an override path exists upstream. Changes to upstream sources (board `.cc`, display classes, `application.cc`) are `-p1` unified diffs in `firmware/patches/`, applied in name order with `git apply` after the mirror; the build fails when a patch no longer applies to the `vendor.lock` commit. To create one, edit a file in the scratch copy after a build, then diff it against the clone:

```bash
cd ~/Projects/weixue-vendor
diff -uN xiaozhi-esp32/main/<path> fw-work/<checkout dir name>/main/<path> > <checkout>/firmware/patches/NN-<name>.patch
```

A diff taken after a build includes the hunks of patches already applied to that file; keep each file's changes in one patch.

## Flash

`build.sh` sources `scripts/env.sh`; `flash.sh` and `backup_flash.sh` use `.venv/bin/esptool` (created on first use). The manual `idf.py` commands below need `source scripts/env.sh` first (see `docs/toolchain.md`).

```bash
source scripts/env.sh
ls /dev/cu.usbmodem*         # one port expected
scripts/backup_flash.sh      # if no full backup of this device exists yet
firmware/flash.sh [port]
idf.py -C ~/Projects/weixue-vendor/fw-work/<checkout dir name> -p <port> monitor   # Ctrl-] to exit
```

`flash.sh` refuses to flash unless `shasum -a 256 -c weixue-build.sha256` passes in the scratch copy, so it writes exactly the image `build.sh` verified and never rebuilds; it writes bootloader (0x0), partition table (0x8000), otadata (0x10d000), app (0x200000) and assets (0xa00000) at 460800 baud. NVS (0x9000 `nvsfactory`, 0x3b000 `nvs`) keeps the same offsets as the stock 32 MB layout and is not erased, so stored Wi-Fi credentials survive. `idf.py -C <work> -p <port> erase-flash` resets everything; restore a backup with `.venv/bin/esptool --chip esp32s3 --port <port> write-flash 0 backup/flash-<timestamp>.bin` after checking its `.sha256`.

Provenance: `flash.sh` prints the `built:`/`current:` lines that differ and stops when `weixue-build.provenance` does not equal `firmware/provenance.sh` run now, for example after a branch switch, a patch, override, board config or `dependencies.lock` edit, a change under `scripts/`, or a different vendored clone or ESP-IDF commit. Commits that touch only other paths (docs, `tasks.yml`, `server/`) keep the build flashable; `build.sh` prints the HEAD it was built at. `scripts/env.sh` returns an error, without exporting ESP-IDF, unless `~/Projects/weixue-vendor/esp-idf` is at the `vendor.lock` esp-idf pin with no local changes and the cmake and ninja that ESP-IDF `export.sh` selects (checked in a subshell first) match their pins.

Backups: `backup_flash.sh` writes `flash-<timestamp>.bin`, `.mac` (device MAC from `flash-id`, read again after the read to confirm the same device) and `.sha256` (one line naming the `.bin`) with mode 0600 in a 0700 directory. `flash.sh` uses only the newest full-size backup whose `.mac` equals the connected device's MAC, and stops unless its `.sha256` is a single line naming that file and the file's sha256 equals it. A backup without `.mac` is never used; `scripts/adopt_backup.sh <backup.bin> [port]` tags it when the NVS `board:uuid` (written by the firmware on first boot and kept by `flash.sh`) in the backup equals the one read from the device's `nvs` partition, writes a `.sha256` if none exists, and sets the files to 0600. The device NVS read goes to a private temporary directory removed on exit.

### Device lock

`flash.sh`, `backup_flash.sh` and `adopt_backup.sh` take the device lock `~/Projects/weixue-vendor/.device-lock` themselves before the first serial access and release it on exit (including errors and SIGINT/SIGTERM). The owner file reads `pid=<pid> since=<UTC> by=<label>`; the owner file is written by rename, so it is never seen half-written. A lock whose pid has exited is taken over (removal happens under an flock on `.device-lock.takeover` and only while the owner file still names the exited pid, so concurrent waiters cannot remove a lock another waiter just took), a live one is waited for (up to `WEIXUE_DEVICE_LOCK_WAIT`, default 2400 s). A lock already held by the caller is used and left in place: the owner pid is an ancestor of the script, or equals `WEIXUE_DEVICE_LOCK_OWNER`. To hold the lock across several commands (flash through the end of an on-device test):

```bash
eval "$(scripts/device_lock.sh acquire 1500)"   # waits like the scripts, then prints export WEIXUE_DEVICE_LOCK_OWNER=<holder pid>; the lock goes stale when the holder exits 1500 s after acquisition
WEIXUE_DEVICE_LOCK_OWNER=<pid> firmware/flash.sh   # in later shells
WEIXUE_DEVICE_LOCK_OWNER=<pid> scripts/device_lock.sh release
scripts/device_lock.sh status                    # free | held: <owner> [live|stale|unknown-format]
```

An owner file in the older `<pid> <date>` form is never taken over; the scripts stop at once with the `WEIXUE_DEVICE_LOCK_OWNER=<pid>` to pass when the caller holds it. `scripts/tests/device_lock_test.sh` runs the lock tests against a temporary directory. `scripts/tests/flash_scripts_test.sh` runs `flash.sh`, `backup_flash.sh`, `adopt_backup.sh`, `provenance.sh` and `nvs_board_uuid.py` on the host against a copy of the checkout with a fake esptool and device image (backup selection by MAC and size, digest and sidecar refusals, provenance and manifest refusals, 0600 modes, NVS `board:uuid` match and mismatch, lock behaviour); it needs the vendored ESP-IDF for the NVS parser and generator.

Evidence (2026-10-07): `docs/logs/fix-firmware-scripts-2-e2e-retry1-2026-10-07.log` (lock acquired by `device_lock.sh acquire` after waiting, `backup_flash.sh` 264 s, `flash.sh` 65 s, 120 s boot from reset with one `Jarvis` + `What time is it?` round), `docs/logs/fix-firmware-scripts-2-tests-2026-10-07.log` (both test scripts, `env.sh` cmake/ninja pin failures leaving nothing exported in bash and zsh), `docs/logs/fix-firmware-scripts-2-e2e-2026-10-07.log` (`backup_flash.sh` 265 s, `adopt_backup.sh` tagging `backup/flash-20261006-163547.bin`, `flash.sh` 64 s, 120 s boot from reset with one `Jarvis` + `What time is it?` round), `docs/logs/fix-firmware-scripts-2-negative-2026-10-07.log` (refusals: `env.sh` pins, provenance after patch and `scripts/` edits, edited provenance file, untagged / other-MAC / misnamed / wrong-hash backups, `dependencies.lock` drift), `docs/logs/fix-firmware-scripts-2-build-2026-10-07.log`.

## Provisioning over USB

`firmware/tools/usb_provision.py` sets the Wi-Fi network and the backend address without the portal and without a rebuild. It writes only the `nvs` partition (0x3b000, 0xd2000 on the 32 MB layout); app, assets and `nvsfactory` are untouched.

```bash
ipconfig getifaddr en0                       # the Mac's current address (Wi-Fi); LAN_IP in server/.env must match
read -r WIFI_SSID; read -rs WIFI_PASSWORD; export WIFI_SSID WIFI_PASSWORD
export OTA_URL="http://$(ipconfig getifaddr en0):8003/xiaozhi/ota/"
.venv/bin/python firmware/tools/usb_provision.py --dry-run   # backup + new image, no write
.venv/bin/python firmware/tools/usb_provision.py             # write, reset, boot-log check
```

| Input | NVS (namespace `wifi`) | Notes |
|---|---|---|
| `WIFI_SSID`, `WIFI_PASSWORD` | `ssid`/`password`/`channel`, `ssid1`..`ssid9` (esp-wifi-connect 3.3.1 `SsidManager`, at most 10) | New SSID at index 0 with `channel` 0 (scan all channels); other saved SSIDs follow in order, an existing entry for the same SSID is replaced. SSID 1-32 bytes, password at most 64 bytes, empty for an open network. 2.4 GHz (ESP32-S3), WPA2/WPA3-Personal or open: esp-wifi-connect has no Enterprise (802.1X) code and no captive-portal login |
| `OTA_URL` | `ota_url` (`Ota::GetCheckVersionUrl`) | Unset: stored value kept. Empty: override cleared, the device uses `CONFIG_OTA_URL`. Otherwise http(s), 10-255 bytes |

Steps (dry runs on this device: `docs/logs/usb-provision-dryrun-2026-10-07.log`): `esptool flash-id` (MAC), partition table read from 0x8000 (`--partition-table <csv|bin>` must agree with it), NVS read to `backup/nvs-<timestamp>.bin` with `.sha256` and `.mac` sidecars (0600), decode of every live entry, new image from an `nvs_partition_gen` CSV (ESP-IDF python env), decode of the new image compared with the intended entries, image kept as `backup/nvs-<timestamp>.new.bin` (0600). Without `--dry-run`: `esptool write-flash <nvs offset>` (hash-verified), RTS reset, boot log printed until `WifiBoard: Connected to WiFi: <ssid>` and an OTA reply (`Activation done` / version check) after `Established new connection to <OTA host:port>`, or `--tail-seconds` (60). Exit 0 when both are seen, 3 otherwise, 2 on an error (nothing is written when the error comes before `write-flash`). Run it with no inputs and `--dry-run` to back up and check the decode of the current NVS only.

Output never contains the input values: SSID, password, OTA URL and its host are printed as `<WIFI_SSID>`, `<WIFI_PASSWORD>`, `<OTA_URL>`, `<OTA_HOST>`, BSSIDs as `<bssid>`; NVS entries are listed by key, type and size. The backups and `.new.bin` hold the credentials in plain text (NVS is not encrypted on this build: `CONFIG_NVS_ENCRYPTION` unset); `backup/` is gitignored.

Kept and lost entries: every other namespace and key is rewritten with its type and value (on this device: `board/uuid`, `phy` calibration, `storage`, `audio`, `websocket/url`, `display`, `bedside`, the rest of `wifi`). The Wi-Fi driver namespace `nvs.net80211` is dropped: `nvs_partition_gen` injects extra entries for its `sta.*`/`ap.*` keys, and this firmware runs the driver with NVS storage off (boot log `wifi:config NVS flash: disabled`). Entries with a bad CRC, incomplete blobs and non-UTF-8 strings are reported as warnings and dropped; an `nvs_keys` partition or an encrypted `nvs` stops the tool. Restore: the printed `write-flash 0x<offset> backup/nvs-<timestamp>.bin` after `(cd backup && shasum -a 256 -c nvs-<timestamp>.sha256)`.

Backend side: the OTA reply carries `websocket.url` built from `LAN_IP` in `server/.env`, so after a Mac address change set `LAN_IP`, re-run `server/scripts/setup.sh` and check `curl http://<LAN_IP>:8003/xiaozhi/ota/` before provisioning. The device and the Mac must be on the same network and that network must let clients reach each other (many office and guest networks isolate clients).

Internet Sharing alternative (network with client isolation or 802.1X): System Settings > General > Sharing > Internet Sharing, share the Mac's uplink (Ethernet, USB adapter or iPhone USB) to devices using Wi-Fi, set the shared network's name and WPA2 password, and provision those as `WIFI_SSID`/`WIFI_PASSWORD`. The Mac is then `192.168.2.1` on `bridge100` (`ipconfig getifaddr bridge100`): set `LAN_IP=192.168.2.1`, re-run `setup.sh`, `OTA_URL=http://192.168.2.1:8003/xiaozhi/ota/`. Wi-Fi cannot be shared while the Mac uses Wi-Fi as its own uplink, and managed Macs can have Internet Sharing disabled. A phone hotspot that both the Mac and the device join works the same way, with `LAN_IP` set to the Mac's address on it (`ipconfig getifaddr en0`); an iPhone hotspot needs Maximize Compatibility on for 2.4 GHz.

Tests: `.venv/bin/python -m unittest discover -s firmware/tests -p 'test_*.py'` (also run by `firmware/tests/run.sh`); the image round-trip and partition-table cases need the vendored ESP-IDF and are skipped without it.

## Face

`FaceDisplay` (board display class base, `11-face-display.patch`) hides the upstream emoji box and draws two pupil-less cyan (`#00E0FF`) rounded eyes on black with LVGL draw primitives (`lv_draw_fill` for the eye, the happy arch and the flat part of a lid, one `lv_draw_triangle` for a lid slant) in each eye object's `LV_EVENT_DRAW_MAIN`. A 33 ms LVGL timer (100 ms while nothing moves in idle/listening) eases the shape toward the target pose and only invalidates an eye whose integer box changed. The theme is forced to dark.

| Mode | Device state | Pose |
|---|---|---|
| idle | idle, starting, activating, Wi-Fi config, upgrading, other | 100x116 eyes; gaze drifts to a random point within ±22/±12 px (35% back to centre) every 1.8-5.5 s |
| listening | connecting, listening | 112x146, taller (156) while VAD reports voice; gaze near centre |
| thinking | listening or speaking after the server's `stt` text, until the first assistant sentence, the turn's `tts stop`, an `Error` status or idle (no time limit) | 108x54 raised and looking up-right, three pulsing dots; no blink |
| speaking | speaking, notifying | 106x122 shaped by the mood, height pulsing with a 3.3 Hz + 5.1 Hz talk wave |

Mood comes from `SetEmotion` (server `llm` emotion, alerts, power save `sleepy`) and shapes idle, listening and speaking: neutral; happy (`happy funny laughing loving relaxed silly winking cool delicious kissy confident`, arch cut from the bottom); sad (`sad crying angry`, outer lids drop); surprised (`surprised shocked`, larger and rounder); sleepy (`sleepy`, half-closed); confused (`confused thinking embarrassed warning cancel cloud_off`, asymmetric). Anything else is neutral. The live backend sends an `llm` emotion (`happy` when the text has no emoji) only for replies streamed as plain text; `direct_answer` tool replies send none and leave the mood neutral.

- Blink: every 3-6 s, 18% of them double; 70 ms close, 40 ms hold, 120 ms open (x1.6 when sleepy).
- Burn-in: the eyes, thinking dots, top bar, status bar and caption move one pixel along an 8-step ring every 60 s; the screen is not scrollable and shows no scrollbar.
- Caption: the upstream chat label (single line, circular scroll), restyled to a 340 px transparent bar 128 px below centre in `#9FB4BC`; it shows assistant `sentence_start` text and system messages. `user` (STT) text clears it and switches to thinking; the next assistant sentence ends thinking. Top-bar icons and the status/clock label are `#6E8A92`.
- Serial: every mode or mood change logs `FaceDisplay: mode=<mode> mood=<mood>`.
- Diag build (`WEIXUE_FACE_DIAG=1`): every 5 s `diag fps=... frame_ms_avg=... frame_ms_max=... voice_flips=...` (rendered LVGL refreshes per second; refresh start to ready, including flush; VAD changes seen by the face); `diag blink`, `diag gaze`, `diag shift` events; 0.8 s after the first occurrence of each mode+mood pair since boot and every 60 s once idle for 5 s, a full-screen `lv_snapshot` logs `diag lit=<screen>% <circle>% ... snap_ms=...` and queues the run-length encoded screen; the `face_diag` task prints it as `FACEDUMP` lines at one line per 20 ms, without the display lock. Each snapshot holds the display lock for about 0.3 s. `.venv/bin/python firmware/tools/face_dump.py <log> <dir>` writes one PNG per dump.

## Ring and bedside page

Sources: `voice_ring.h` (ring state and invalidation tiles), `bedside_schedule.h` (night window and hint), the ring, clock and page switching in `face_display.cc`, and `firmware/patches/21-ring-bedside.patch` (`AudioService::GetOutputLevel`, `Application::GetSessionOrigin`, the `urgent` field of the proactive poll, touch and MCP tool on the board, `CONFIG_WEIXUE_BEDSIDE_START`/`END`).

Ring: a 9 px band (2% of the 466 px diameter) whose outer edge is 1 px inside the panel edge, drawn above everything from the face timer: a solid ring is one A8 coverage mask (466x466, PSRAM, built at boot) blended in the ring colour, the spin is `lv_draw_arc` steps each clipped to its own sector box. The ring is split into 20 tiles of 18° and only tiles whose content changed are invalidated; a full repaint is about 56k px, so a solid ring repaints at most every 100 ms and the spin every 66 ms (a new style or colour at once).

| Face mode | Ring |
|---|---|
| idle | off |
| listening | cyan, opacity pulsing between 64 and 224 in 6 levels at 0.8 Hz |
| thinking | 120° arc rotating clockwise at 180°/s, fading from a cyan head to a blue tail in 12 steps |
| speaking | cyan; opacity 48-224 in 32-step levels follows the RMS of the PCM frame being played (-50..-6 dBFS, 30 ms attack, 150 ms release) |
| error | red, 300 ms on / 300 ms off for 1.8 s after the status shows `Error` (network or server failure alert); continuous in the fatal-error state |

Bedside page: a seven-segment `HH:MM` clock (`#701000`, 60x112 px digits) 26 px above centre and two 84x6 px closed-eye lines (`#5A0C00`) 96 px below it; top bar, status bar and caption are hidden; the ring keeps its states in `#801400` at 55% opacity (error stays red). The page and eyes move 6 px along the 8-step burn-in ring every 60 s; `--:--` shows until the clock is set (OTA response or a proactive poll's `Date` header, see Device behaviour). ## Device behaviour

- OTA: POST `CONFIG_OTA_URL` (NVS `wifi/ota_url` overrides it when non-empty; the Wi-Fi portal's Advanced tab sets it, an empty submit writes `""` and restores the default). The response's `websocket.url` is where the device streams audio. While the server is unreachable the device retries 10 times with doubling delays (about 85 min).
- Wake word: the ESP-SR model `wn9_jarvis_tts` detects "Jarvis" and sends `{"type":"listen","state":"detect","text":"Jarvis"}`. Exactly one `AfeAudioEngine: Model 0: wn9_jarvis_tts` line appears at boot.
- Wake capture (`23-application-wake-capture.patch`): in idle and notifying, a WakeNet detection switches the running AFE straight to voice processing (no AFE buffer reset, no input warm-up), so the microphone stream continues from the frame after the wake word. Packets encoded while the audio channel opens are held (at most 50, 3 s); once it is open the device sends the 1.98 s wake-word audio, then the held packets (`Sent N packets captured after the wake word`), then `listen detect` and `listen start`, and streams on. A short request said in one breath with the wake word reaches the server whole (see Wave 3 fixes below).
- Session log (`38-application-session-counts.patch`): every idle -> connecting transition logs `Session start: <wake_word|toggle|start_listening|proactive|proactive_urgent>` (`toggle`: BOOT click, `Application::ToggleChatState`; `start_listening`: `Application::StartListening`; `wake_word`: WakeNet or `WakeWordInvoke`; `proactive*`: the proactive poll), and every audio channel close logs `Audio channel closed: <n> packets sent, <n> dropped, oldest sent <ms> ms after encoding` (microphone and wake-word packets the transport accepted, and those dropped after it refused one, since the channel opened; the largest encode-to-send time among the microphone packets, about 0.4 s for the packets held while a wake opens the channel).
- Clock (`27-clock-posix-tz.patch`): the system clock is UTC. When the OTA response's `server_time` has `tz` (a POSIX TZ string, `docs/server.md`), the device sets `TZ` from it, stores it in NVS (`clock/tz`, applied at the next boot before any OTA response) and logs `Clock: TZ <tz>, UTC offset <now> min (January <std>, July <dst>)`; local time, the bedside hours and the status bar follow the TZ's daylight saving rules. Without `tz` it adds `timezone_offset` to the clock as before and clears the stored TZ. Every proactive poll answered 200/204 resyncs the UTC clock from its `Date` header (an IMF-fixdate with a valid calendar date and nothing after `GMT`) when they differ by 2 s or more (`Clock: resynced from the backend Date header (was <drift> s)`), so a clock that the boot OTA did not set is set by the first answered poll.
- Wi-Fi provisioning (no stored SSID): join the `Xiaozhi-XXXX` hotspot and follow the on-screen portal URL, or write the credentials over USB (see Provisioning over USB).
- Power (ADR-12, `firmware/patches/05-board-power-usb.patch`): after 60 s idle the screen dims to 20 %. After `CONFIG_WEIXUE_SCREEN_OFF_SECONDS` idle (default 300, `0` = never), on USB and battery, the panel turns off (CO5300 DISPOFF, brightness 0) and logs `Panel off after 300 s idle (VBUS present|absent)`; MCU, Wi-Fi and wake word detection keep running. Wake word, touch (LVGL `LV_EVENT_PRESSED`), IMU pick-up or face-up (see IMU gestures), any `SetPowerSaveLevel` above low power (session start, notification, upgrade) or the device leaving idle (checked every second) turns it back on (`Panel on`) and restores the dim. Idle PMIC power-off happens only while the AXP2101 reports no VBUS, after `CONFIG_WEIXUE_BATTERY_IDLE_POWER_OFF_SECONDS` (default 300, `0` = never); set either in `config.weixue.json` `sdkconfig_append`. On USB the board logs `Idle power-off skipped: VBUS present` once per idle period; unplugging USB during that period wakes the screen and restarts the battery countdown. Boot logs `VBUS present|absent, battery present|absent, idle power-off on battery after N s, panel off after N s`. USB idle check: `docs/logs/fix-power-usb-idle-usb-2026-10-06.log` (300 s) and `docs/logs/fix-power-usb-idle-usb-test90-2026-10-06.log` (test build with 90 s). Panel-off check: `docs/logs/fix-screen-off-device-2026-10-06.log` (see Panel off below).
- Device AEC is on; listening mode is realtime (barge-in). BOOT double-click toggles AEC until reboot.
- Proactive poll (`firmware/patches/10-proactive-poll.patch`): while idle the device long-polls `/weixue/proactive/poll` on the OTA host and, on `200` with `speak` true, opens a session with `listen detect` text `weixue:proactive:<id>:<lease>` from that poll answer (`firmware/patches/36-proactive-invoke-lease.patch`, `weixue_agent::InvokeText`: 1-64 characters of `[0-9A-Za-z_-]` each, else the bare `weixue:proactive`; `docs/proactive.md`); a `200` body that did not arrive whole (`Proactive poll body unreadable (<got> of <Content-Length> bytes)`) opens nothing and is polled again after 1 s.
- Custom messages: `CONFIG_RECEIVE_CUSTOM_MESSAGE=y`. A server message `{"type":"custom","payload":{...}}` logs `Received custom message:` and shows the payload as a system chat line; a non-object payload logs `Invalid custom message format`; an unknown `type` logs `Unknown message type`.
- Audio: the device decodes 16 kHz server audio and resamples to its 24 kHz output; each session logs `Server sample rate 16000 does not match device output sample rate 24000, resampling may cause distortion`.
- OTA firmware updates: the device reports `board.type` = `esp32-s3-touch-amoled-1.75` (the board directory, not the weixue build name), and the server offers any `server/data/bin/esp32-s3-touch-amoled-1.75_<version>.bin` newer than 2.5.1, which would replace this firmware. Keep `server/data/bin` free of such files; self-hosted OTA updates need a weixue-specific board type first.
- Network constraint: the device must reach the backend host on the LAN. On a Mac running Cisco Secure Client, `192.168.8.0/24` routes into the VPN tunnel while it is connected and the device's OTA connect to `:8003` fails with `connect_failed, native=113`; device sessions need the VPN disconnected or local LAN access allowed.

## IMU gestures

Sources: `firmware/overrides/main/boards/waveshare/esp32-s3-touch-amoled-1.75/qmi8658.{h,cc}` (driver), `imu_gestures.h` (pick-up and face-down detection), `firmware/patches/20-board-imu-gestures.patch` (board wiring, MCP tool, mute glyph), `firmware/patches/12-application-mic-mute.patch` (`Application::SetMicMuted`).

- Driver: QMI8658A on the board's `I2C_NUM_0` bus (SDA 15 / SCL 14), probed at 0x6B then 0x6A (`WHO_AM_I` 0x05). Soft reset, accelerometer only, ±4 g at 500 Hz, little-endian, INT1/INT2 high-Z, CTRL9 handshake on `STATUSINT.bit7`. A board without the sensor boots without IMU features (`QMI8658 not found`).
- Polling: one task (`imu`, priority 2) reads `TIMESTAMP` with the acceleration (one burst, 0x30-0x3A) and `STATUS1` every 20 ms; when `STATUS1.TAP` is set it reads `TAP_STATUS`. `TIMESTAMP` is not latched, so a read can straddle an increment (255 counts off); the counter is used once a re-read agrees within 16 counts (up to two re-reads, `IMU sample counter re-read (count)` when the first read was torn; no agreement is a failed read). A missed 20 ms deadline restarts the schedule instead of catching up. Each poll goes through `ImuPoll` (`imu_gestures.h`, shared with the host test): `ImuSampleGate` measures each sample's spacing with the sensor sample counter (500 Hz, 2 ms per count): fewer than 5 counts (10 ms) since the last accepted sample is a repeated or catch-up read and is not used; 5-50 counts (10-100 ms) is the next sample, and the detector's rest and orientation timers advance by the measured time, not a fixed 20 ms; more than 50 counts, or the first sample after a failed read, restarts the series and resets the detector's filter history and its rest, pick-up and orientation timing (`IMU resync after N ms without a sample (count)`, logged for the first 5 and every 100th).
- Double-tap: the QMI8658 Tap engine (datasheet Table 35 example parameters at 500 Hz: PeakWindow 20, TapWindow 50, DTapWindow 250 samples, alpha 0.0625, gamma 0.25, PeakMagThr 0.8 g², UDMThr 0.4 g²). `TAP_NUM` 2 is a double-tap; every engine report is logged as `IMU tap: status1=… tap_status=…`. Action: `speaking` → `AbortSpeaking` (the BOOT-click path), `notifying` → `StopListening` (stops the notification).
- Pick-up: after the median-filtered acceleration (5 samples per axis) has stayed within 0.04 g for 1 s, a deviation above 0.12 g from that rest vector for 3 consecutive samples. Action: the board's display wake (as touch): leaves the 60 s dim state, turns the panel back on after the 300 s panel off and restarts both idle counts. The Any-Motion and Wake-on-Motion engines are not used: Any-Motion thresholds are per-sample slopes in 1/32 g at the 500 Hz Tap ODR, and WoM mode produces no sensor data.
- Face-down: screen-normal component below -0.8 g with |a| within 0.2 g of 1 g for 800 ms; face-up: above -0.5 g for 300 ms. The screen normal is the sensor +z axis times `kScreenNormalSign` in the board patch.
